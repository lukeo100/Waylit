# PWA shell

This page describes the installable app shell as built: the manifest, the service worker, install, landscape and fullscreen handling, screen wake lock and the first run safety notice. It also lists the limits of a progressive web app, so later phases plan around them.

Status: the shell is covered by unit tests and was checked in headless desktop Chrome (see [What has been verified](#what-has-been-verified)). The owner installed the deployed app on a Samsung Galaxy A35 and reported that the HUD works well. The fullscreen display mode added after that test has not been checked on the phone yet.

## Install on Android Chrome

1. Deploy a copy over HTTPS, see [DEPLOYING.md](DEPLOYING.md). A service worker and install need HTTPS, or `localhost`.
2. Open the URL in Chrome on the phone and wait a few seconds on the start screen.
3. Tap **Install app** on the start screen. If the button does not appear, open the Chrome menu and choose **Install app** or **Add to Home screen**.
4. Launch Waylit from the home screen icon. It should open fullscreen with no address bar, no Android status bar or navigation bar, in landscape, with no website header or sidebar.

**Reinstall after the manifest changed.** Android Chrome reads the manifest when the app is installed and only updates some of it afterwards. An app installed before `display` changed from `standalone` to `fullscreen` may keep showing the system status bar and navigation bar. Uninstall it from the home screen and install it again to pick up the fullscreen display mode. Until then the riding screen still asks for fullscreen from the **Start trip** tap, which hides the bars in most cases.

Samsung Internet and other Chromium browsers on Android also install it. Safari on iOS has no install event, so the start screen shows a hint to use Share, then Add to Home Screen. iOS support is not a goal of milestone 1.

## Test on a phone with remote debugging

You do not need a deployment to test on a real phone. Port forwarding makes the phone see your computer's dev or production server as `localhost`, which counts as a secure context.

1. On the phone, enable Developer options (tap the build number in Settings, About phone, seven times), then turn on **USB debugging**.
2. Connect the phone to your computer with a USB cable and accept the debugging prompt on the phone.
3. In desktop Chrome open `chrome://inspect/#devices`. Tick **Discover USB devices**.
4. Click **Port forwarding**, add port `3100` mapped to `localhost:3100`, and tick **Enable port forwarding**.
5. On the computer, build and serve the production build, because the service worker only registers in production:

   ```sh
   pnpm build
   PORT=3100 pnpm start
   ```

6. On the phone, open Chrome and go to `http://localhost:3100`.
7. Back on `chrome://inspect/#devices`, click **inspect** under the phone's tab. In DevTools, the **Application** panel shows the manifest, installability errors, the service worker and Cache Storage. **Lighthouse** can audit the live page.

To test offline behaviour, install the app, open the start screen and the ride screen once online, stop the server, put the phone in aeroplane mode, and relaunch. In DevTools, ticking **Offline** on the Network panel does not affect the service worker's own requests, so use a real disconnect or stop the server.

### What to check on the device

- The install button appears, and the installed app launches fullscreen in landscape, with the status bar and navigation bar hidden.
- After **Start trip** the system bars stay hidden, and after **End trip** the app is no worse off than before. A swipe from the screen edge shows the bars for a moment and they hide again (see the limits below).
- Nothing sits under the camera cutout or the rounded corners: the speed, minimap, time and the dock all have space around them.
- The ride screen shows no address bar, header, sidebar or install button.
- The screen stays on while a trip is running (after **Start trip**), and turns off normally after **End trip** or after leaving the ride screen.
- Rotating to portrait on the ride screen shows the "Turn your phone sideways" prompt, and rotating back hides it.
- The first run safety notice appears once, and not again after tapping **I understand**.
- After a second deploy, the start screen offers **Reload** and the new version loads afterwards.
- Offline, pages already opened still load, and anything else shows the offline page.

## Manifest

Generated by `apps/web/src/app/manifest.ts` and served at `/manifest.webmanifest`.

| Field | Value |
|---|---|
| `name`, `short_name` | Waylit |
| `display` | `fullscreen` |
| `display_override` | `fullscreen`, then `standalone` as the fallback |
| `orientation` | `landscape` |
| `start_url`, `scope` | `/?source=pwa`, `/` |
| `theme_color`, `background_color` | `night950` from the design tokens |
| `icons` | 192 and 512 pixel PNGs for `any` and for `maskable` |

The icons are an original logo (three stacked route chevrons) drawn by `apps/web/scripts/generate-icons.mjs`. The script has no dependencies and its output is identical on every run. To regenerate after changing the logo, run `pnpm --filter @waylit/web icons` and commit the files in `apps/web/public/icons/`. The whole drawing sits inside the central 80 percent circle, the maskable safe zone, so one design serves both purposes.

## Service worker

`apps/web/public/sw.js` is hand written and has no dependencies. Its rules live in `apps/web/public/sw-strategy.js` so they can be unit tested. Both are plain scripts, served as they are.

Registration happens only in production builds (`ServiceWorkerRegistrar`), because development serves unhashed files that must not be cached.

### What it caches

| Request | Strategy | Cache |
|---|---|---|
| Page loads (navigations) | Network first. On failure, the last saved copy of that page, then the offline page | `waylit-pages-v2`, capped at 20 entries |
| `/_next/static/*`, `/icons/*`, the manifest and other same origin images, fonts, scripts and styles | Stale while revalidate | `waylit-static-v2`, capped at 120 entries |
| Offline page, start page, manifest, icons | Saved at install | `waylit-shell-v2` |

Build assets have content hashes in their names, so a saved copy is always the right copy for its URL. After the first load, the page tells the worker which assets it already loaded, so the first offline launch works. The worker only accepts same origin build assets in that message.

### What it never caches

- Requests to any other origin. That includes every map tile server and third party API (Google 3D Tiles, Cesium ion, OpenFreeMap, Mapterhorn).
- `/cesium/` and `/maplibre/`, the map renderers' workers and WebAssembly files. They are large, change with the dependency versions and are cached by the browser's normal HTTP cache.
- `/api/` routes, non GET requests, range requests and Next.js data requests.
- Error responses and opaque responses.

**Map tiles and terms.** Caching of any third party map tiles must follow the provider's terms. Many providers restrict or forbid storing tiles. The worker leaves tile requests alone by default, and the comment in `sw.js` says so. If a later phase adds tile caching for a provider whose terms allow it, put it in its own size capped cache and record the terms in `docs/THIRD_PARTY.md`.

### Versions and updates

- Cache names carry a version, set by `VERSION` in `sw-strategy.js`. When a new worker activates it deletes old Waylit caches. Bump `VERSION` whenever `sw.js`, `sw-strategy.js`, `offline.html` or the precache list changes.
- A new worker waits instead of taking over, so an update never swaps files under a rider mid trip. The start screen shows "A new version of Waylit is ready" with a **Reload** button. Tapping it activates the new worker and reloads once. The prompt is never shown on the ride screen.
- The page checks for a new worker each time the app returns to the foreground. The browser also re-checks at launch.
- The worker scripts are served with `Cache-Control: no-cache` (see `headers()` in `next.config.ts`). A static host or web server must set the same header for `/sw.js` and `/sw-strategy.js`, or updates can be delayed by days.

### Offline page

`apps/web/public/offline.html` is self contained: inline styles, no scripts and no external files except the icon. It uses the design tokens, copied as CSS variables, and a test fails if the values drift from `packages/ui-tokens`.

## Install flow

`InstallPromptCapture` (root layout) keeps the browser's `beforeinstallprompt` event for the whole session. `InstallPrompt` shows a small **Install app** button on the start screen when the event is available, and a short text hint when it is not (after a short delay, so it does not flash). It renders nothing when the app is already installed or running standalone, and it is not used on the ride screen.

## Landscape and full screen

- The manifest asks for landscape and `fullscreen`, with `display_override` set to `fullscreen` then `standalone`, so a browser that cannot do fullscreen installs the app as standalone instead. Fullscreen hides the phone's status bar (clock, notification icons, battery) and navigation bar while the app is open, so the riding screen draws its own top strip: the time, temperature and online dot are top right, and the speed and turn are top left.
- The viewport uses `viewport-fit=cover`, so the app can draw under the camera cutout, rounded corners and system bars.
- Safe area insets are exposed as `--wl-safe-top`, `--wl-safe-right`, `--wl-safe-bottom` and `--wl-safe-left`. Ordinary pages are padded by them. The ride screen is fixed and uses them for its own spacing: the top area, the dock row, the credits strip and the trip summary all keep at least the inset (and a small minimum margin for rounded corners) from every edge, so nothing sits under the camera cutout.
- On the ride screen, a phone narrower than 768 pixels held upright shows a "Turn your phone sideways" prompt (`RotateOverlay`, CSS only).
- From the start screen, the **Open ride screen preview** click also tries `screen.orientation.lock("landscape")`. It only runs in the installed app, only after that tap, and fails silently if the browser refuses.
- **Fullscreen API on the riding screen.** `apps/web/src/pwa/fullscreen.ts` requests fullscreen for the whole page from the **Start trip** tap (a user gesture), but only when the page is not already fullscreen and the installed app is not already in `display-mode: fullscreen`. It is feature detected and fails silently, so a refusal never breaks the ride. When the trip ends, or the rider leaves the screen, it exits fullscreen if the API entered it. This is what hides the system bars in a normal browser tab, and in an installed app that predates the manifest change. `isStandalone()` also counts `display-mode: fullscreen`, so the install button stays hidden in the fullscreen app.

## Screen wake lock

`apps/web/src/pwa/wake-lock.ts` holds the logic and `use-wake-lock.ts` is the React hook. The ride screen calls `useWakeLock(true)` only while a trip is running, so the lock is released as soon as **End trip** is pressed. It requests a screen wake lock, asks again whenever the page becomes visible (the browser releases the lock when the page is hidden), and releases it on unmount. It is feature detected, and a refused or missing lock does nothing and never throws.

## Location permission (live GPS)

Phone GPS is off by default. When the rider chooses **Phone GPS** and taps **Start ride**, the page calls `watchPosition` from that tap (a user gesture), so the browser's location prompt appears then and not before. The start screen says first what will be asked and that the location stays on the device. If the rider blocks it, the ride shows an amber note and the browser setting has to be changed (the icon beside the address), then the trip started again. The screen wake lock is already held while a trip runs, so GPS keeps updating with the screen on. Background tracking is not supported by a PWA: if the page is hidden, the browser may stop location updates, and the ride shows the signal as lost until it returns. Not verified on a real phone yet.

## First run safety notice

`SafetyNotice` (root layout) shows once: Waylit is a navigation aid, not a safety system, follow local road rules, do not interact with the screen while riding, provided without warranty. The acknowledgement is stored in `localStorage` under `waylit:safety-notice-ack:v1`. Storage access is wrapped in try and catch. If storage is blocked, the notice is not shown again for the rest of that page session and nothing throws. Change the version suffix in the key if the wording changes enough that riders should read it again.

The map settings (which map, how strong the hologram screen effect) are stored the same way under `waylit:map-settings:v1`, also inside try and catch. They are preferences only, so blocked storage means they are not remembered. The service worker and its caches are not affected: the map switch adds no files and no network requests of its own.

## Limits of a PWA

Plan later phases around these.

- **Web Bluetooth** works on Chromium browsers on Android and desktop, and not on iOS. It needs HTTPS and a user gesture, so the MAX G3 adapter connects only from a tap on Connect. GATT connections and notifications work on Chrome for Android with no flag, but `getDevices()` and advertisement watching are not reliable there, so the browser's chooser is shown every session. A phone with the screen off drops the link, so the app keeps the screen awake while the scooter is linked and tries to reconnect when the screen returns. The adapter is Android Chrome only until the Expo app exists. iPhone and iPad browsers cannot use it, and the Vehicle section says so. See [VEHICLE.md](VEHICLE.md).
- **Background location is unreliable.** Browsers pause or throttle geolocation and timers when the page is hidden or the screen is off. A ride needs the screen on and the app in the foreground, which is why the wake lock exists. True background tracking is a reason for the later native app.
- **Wake lock is a request.** The browser can refuse it, for example in battery saver, and releases it whenever the page is hidden.
- **Storage is not guaranteed.** Browsers can evict site data under storage pressure, and caches have size limits. `navigator.storage.persist()` asks the browser to keep data, and installed apps are treated more generously, but it is still a request. Keep anything valuable recoverable.
- **Orientation lock** only works in some contexts, so the manifest and the rotate prompt remain the main handling.
- **System gestures still work.** In fullscreen, swiping from the edge of the screen (or the Android back and home gestures) can reveal the system bars temporarily. They hide again after a moment. The app cannot prevent this and should not try. Fullscreen can also be refused by the browser, so the manifest and the Fullscreen API are both used.
- **Install behaviour differs by browser.** Chromium fires an install event, Safari and Firefox do not.
- **Hardware access** such as sensors, USB and NFC varies by browser and may need permissions.

## What has been verified

Automated, in `pnpm test`: the fullscreen request and exit logic with fake browser objects (skipped when already fullscreen, silent on refusal), cache classification and eviction rules, the real `sw.js` run against fake caches (precache, activate cleanup, network first pages, offline fallback, stale while revalidate, API and cross origin requests ignored), update flow, wake lock behaviour with mocked browser APIs, install event handling, orientation lock, safety notice storage including blocked storage, manifest fields and icon files, and the offline page tokens.

Manual, in headless desktop Chrome against a production build, on localhost:

- The manifest and worker scripts are served with correct types, and the worker scripts with `no-cache`.
- Chrome reports no manifest errors and no installability errors.
- The worker registers, activates, takes control and fills its caches. After the server is stopped, the start page, the ride page and the start URL load from cache, and an unvisited page shows the offline page.
- The ride screen has no header, nav or sidebar, and no install UI. The rotate prompt shows in a 390 by 844 viewport and is hidden at 844 by 390.
- The wake lock requested on the ride screen reports active while a trip runs, and inactive after End trip.
- The safety notice shows on first run, and its acknowledgement is stored.

Not verified: the fullscreen launch on the Samsung Galaxy A35 and whether the system bars stay hidden after a reinstall, the real wake lock behaviour with the screen timeout, the `beforeinstallprompt` flow on the phone, a Lighthouse audit, and update prompts across a real second deploy.
